# HDS Android 移植任务书与执行计划

版本：1.0 · 编制日期：2026-10-13（Asia/Shanghai）

本交付物是供后续模型实施的计划包。已完成四个参考仓库及关键依赖的源码/文档调查；没有开发 APK，没有验证手机运行结果。文中的新接口、目录、性能指标和阶段安排均为拟实施设计，不能当作现成功能。

## 1. 已确认需求

| 项目 | 用户明确要求 |
|---|---|
| 移植对象 | `ISEKAI-MomoiCore/HDS-Interlude`，即 Koishi 插件本体 |
| 平台 | 首版 Android APK，iPhone 后续再考虑 |
| 运行方式 | 手机独立运行，直接连接模型 API，不依赖持续开机的电脑或服务器 |
| 保真目标 | 尽量还原电脑版 HDS，包括剧情、记忆、调度和配置能力 |

| 新增能力 | 角色卡导入及相关管理；需让导入内容实际参与 HDS 叙事 |
| 界面 | 极简风格，中文优先 |
| 设备 | 用户有 iQOO 15，希望尽量扩大兼容范围 |

## 2. 技术结论

推荐：**Kotlin 原生运行管理 + Capacitor/React 手机界面 + PRoot/Ubuntu ARM64 + Node/Koishi/HDS 原核心**。QQ 通道采用可替换的本地 OneBot 后端；全功能路线优先验证 SnowLuma，NapCat 作为私聊/群聊参考及兼容后端。

理由：HDS 的服务层与 Koishi 数据库、会话、定时器和投递机制紧密相连。先保留原核心，比把全部逻辑重写为 Kotlin/Dart 更有利于保持行为。DeepSeek 安卓仓库提供可参考的 Kotlin 运行管理；Bubble 仓库补足 Linux QQ/NapCat 安装和账号管理经验。

**首个里程碑必须验证 QQ 空间，不能先把界面做完。** HDS 空间功能使用 SnowLuma 的扩展动作，普通 OneBot/NapCat 聊天成功不能证明空间可用。SnowLuma 官方将 Android + PRoot 标为实验路线，进程注入与 PRoot 的相互影响是已知不确定性。[来源](https://snowluma.github.io/en/docs/guide/deploy/mobile)

另一个前置事项是 SnowLuma 的分发条件：它不是普通 MIT/BSD 依赖。应先记录使用方式、原生组件来源和授权边界；涉及其代码改造或打包发布的部分必须先核清，不得因为仓库可见就直接复制进产品。[许可证](https://github.com/SnowLuma/SnowLuma/blob/87527cb7641a5a42f8f0efb73cb066102e004dee/LICENSE)

## 3. 完成标准

最终交付为可复现构建的 Android 项目、安装包、源代码与修改清单、测试报告、用户手册、备份恢复说明。以下全部成立才可称“首版完成”：

1. 手机内启动 HDS 和所需 QQ 运行环境，无远程计算机依赖；模型推理仍由用户配置的 API 完成。
2. JSON/PNG 角色卡导入，预览后创建角色与故事；世界书、开场白、示例对话与兼容性差异可查看。
3. QQ 私聊、群聊、空间读取/发帖/评论/点赞及 HDS 对动态的叙事感知通过验收。
4. 持续叙事、记忆压缩、Overlay、日程、主动联系、延迟与分段消息保持 HDS 基线语义。
5. 退出界面、断网、进程重启后数据一致；不能把“未发送”写成“已发送”。
6. iQOO 15 真机通过主要用例，兼容设备范围有实际证据；未测设备标为未测。
7. 安装、升级、回滚、备份/恢复均可操作，不要求用户自己敲终端命令。

内部原型可逐步交付，但缺少空间功能的原型不能标为满足用户要求的首版。

## 5. 范围管理

首版实现 HDS 已有功能及必要手机入口。Live2D、TTS 合成、模型本地推理、任意 AstrBot 插件、AI 操作其他手机应用不是本次已确认需求，不混入关键路径。HDS 当前的原生语音输入、图片理解、贴纸和浏览能力则必须纳入兼容盘点与验收；不能把它们与新增 TTS/Live2D 混为一谈。

角色库可存多个角色；首版默认一个活动故事运行。HDS 当前服务会选出一个 Canonical Story 并归档其他活动故事，因此多个角色同时独立生活需要多个隔离实例，属于后续扩展，不能仅在同一库中多插几行实现。角色切换必须保存各自剧情；多个 QQ 端点服务同一个故事与多个故事并行是两件事。

默认先做个人使用/内测 APK。公开发布、商用、应用商店上架尚未确认，作为分发阶段决策；这不妨碍完成 HDS 核心、导入器和不含受限组件的基础壳。

## 6. 初始适配目标

计划以 `minSdk 26`（Android 8）作为尽量扩大覆盖的工程起点，运行时首批支持 `arm64-v8a`。这只是待验证目标，不是已确认最低配置。参考工程使用 target/compile SDK 35；T01 应核对实施时工具链并固定版本，升级 target 后须重做行为测试，不能靠降低 target 避开系统限制。

以 iQOO 15 为主验收机；实施时采集真实 Android/OriginOS 版本、RAM、ABI、内存页大小及 WebView 版本，不从型号推断。补测一台较旧的 ARM64 Android 手机和一个其他厂商设备。32 位 ARM、x86、Android 7 及以下、iOS 不纳入首版承诺；保留协议与 UI 可移植性。

安装前根据运行时清单计算临时解包空间、最终空间和回滚空间，显示实际需求。不得承诺固定小体积或低内存：QQ/Electron 与 Linux 用户空间的真实占用要由 T02/T16 测出。

## 7. 阶段与投入估算

以下为具备 Android、Node 与 Koishi 经验的开发者“有效人日”规划，非模型运行时长、非工期承诺；关键验证失败会重估。

| 阶段 | 内容 | 预计投入 | 出口 |
|---|---|---:|---|
| G0 | 基线、依赖分发调查、iQOO 上的 QQ+空间可行性 | 4—8 人日 | 可复现验证报告；决定全功能后端 |
| G1 | 原生壳、安装器、服务监管与 HDS 宿主 | 6—10 人日 | 首个本地端到端原型 APK |
| G2 | 角色卡、世界书、手机 API、极简界面 | 7—12 人日 | 可日常配置与使用 |
| G3 | QQ/空间完整集成、媒体与 HDS 高级能力 | 7—12 人日 | 功能保真矩阵完成 |
| G4 | 恢复、备份、升级、兼容性和打包 | 6—10 人日 | 首版候选 APK 与报告 |

合计约 30—52 有效人日。推荐同一模型逐阶段推进；更换模型时通过任务编号和交接记录接续。第一轮只要求完成 T01—T03，不要求一次做完整产品。

## 8. G0 失败时如何继续

若 SnowLuma 在 iQOO 15 上无法免 Root 运行，先给出具体失败层级与最小复现，检查可替换本地后端是否实际具备等价空间动作。没有技术证据时不能宣称换成 NapCat 即可解决。继续完成不依赖该后端的导入器、UI、HDS 宿主与测试；把全功能发布门槛保持为未通过。

不得擅自改成远程服务器、强制 Root、删除空间需求或将未验证功能标为支持。只有当验证结果证明必须改变用户约束时，再携带完整报告询问取舍。未通过分发条件时也不把受限组件打入公开 APK。
